Closet Prayer / Administrator console

Set up the Google connection

A new-project guide for the console operator. Updated October 4, 2026.

This is a connection preview, not the finished management console. Account connection and group reading are implemented. Approval, editing, and group configuration still use the existing spreadsheet workflow. Real Google sign-in must be tested after these settings are supplied.

Who does this setup?

The operator of console.closetprayer.com completes this once for the hosted console. Each church does not need its own Cloud project just to use that console. Churches keep their own spreadsheets and Apps Script deployments, and share spreadsheet Editor access with their administrators.

A self-hosted copy needs its own Google client and API key, with its own website addresses. There is no central prayer database or administrator-count restriction in this application. Google quotas and organization policies still apply.

1. Create a Cloud project

  1. Open Google Cloud's new project page with an account that will remain responsible for Closet Prayer. Give the project a recognizable name such as Closet Prayer Console.
  2. Select the new project. Record its project number from the project dashboard. This is the numeric value, not the project name or the hyphenated project ID.
  3. In APIs & Services > Library, enable Google Drive API, Google Sheets API, and Google Picker API. Keep all three in this same project.

No Firebase database, Cloud Run server, service account, or paid hosting deployment is needed by this implementation. Do not turn on unrelated services.

2. Configure Google authorization

Open Google Auth Platform > Branding inside Google Cloud Console, and confirm that your Closet Prayer project is selected at the top. Choose Get started if needed. Set the app name, a real support email, and a monitored developer contact. Use an External audience so administrators from different churches can connect. Keep the app in Testing initially and add the Google accounts you will test under Audience > Test users. Follow Google's consent-screen guide if the menu labels differ.

In Data Access, request only these scopes:

openid
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/drive.file

The first three identify the connected account. drive.file gives access to files selected for this app, including previously authorized files. It includes write permission, although this preview performs only reads. Do not replace it with whole-Drive or all-spreadsheets access. Google supports this per-file scope for the Sheets API; it cannot be restricted to individual tabs within a selected file.

For production branding, use the console home page and https://console.closetprayer.com/privacy.html. Review that notice and your support contact before submitting them. Add closetprayer.com as an authorized domain and complete Google's ownership/branding checks as requested. Testing is not a substitute for any verification Google requires before public release.

3. Create a web OAuth client

Under Google Auth Platform > Clients, create a client of type Web application. Add these Authorized JavaScript origins:

https://console.closetprayer.com
http://localhost
http://localhost:5174
http://localhost:4175

Use only the origins you actually need. Origins have no path, trailing slash, or wildcard. Use localhost, not a Tailscale IP, for local Google sign-in testing. Mobile testing of the Google connection should use the configured HTTPS console domain.

Record the client ID, ending in .apps.googleusercontent.com. The console uses Google's browser popup flow and needs no redirect URL or client secret. Do not put a secret in source code, repository variables, or chat. See Google's client setup guidance.

4. Create and restrict the Picker API key

In the same project's APIs & Services > Credentials, create an API key and edit its restrictions immediately. If you already created the key, open that existing key rather than replacing it.

Under Application restrictions, choose Websites (HTTP referrers). Allow:

https://console.closetprayer.com/*
https://docs.google.com/*
http://localhost:5174/*
http://localhost:4175/*

The Google Docs address is required: the file picker runs inside a Google-hosted frame. Omitting it can cause The API developer key is invalid even when the key was copied correctly. These are the API key's website restrictions, not the OAuth client's Authorized JavaScript origins. See Google's explanation of Picker website restrictions.

Under API restrictions, choose Restrict key and select both Google Picker API and Google Drive API, following Google's web Picker setup example. Keep both APIs enabled in the project. The console's own Drive and Sheets reads still use OAuth; this does not broaden the requested account permissions. Keep the OAuth client, API key, and numeric project number in the same project.

Save the restrictions, allow a few minutes for the changes to take effect, then reload the console and try choosing a spreadsheet again. Changing restrictions on the existing key does not require changing the GitHub variable or rebuilding the site. If the key value itself changes, update the variable and redeploy as described below. Keep the key restricted; do not make the spreadsheet public to resolve this error.

A browser API key is visible in the published website. Restricting it is essential; hiding it in a build secret does not make it private. The key identifies the project, but does not by itself grant access to a church's spreadsheet.

5. Add the three public settings

For the hosted console, open the repository's Actions variables and add these repository variables:

NameValue
VITE_GOOGLE_CLIENT_IDThe web client ID
VITE_GOOGLE_API_KEYThe restricted browser Picker key
VITE_GOOGLE_PROJECT_NUMBERThe numeric project number

Then run Actions > Deploy console > Run workflow. These values are inserted when the site builds, so changing a variable alone does not update the live site. Missing or invalid configuration leaves Google connection disabled.

For local testing, the same three names belong in an ignored .env.local file, following .env.example. Restart the local development server after changing them. Never commit personal tokens, prayer records, a client secret, or an unrestricted key.

6. Connect the subdomain

First set the repository's Settings > Pages source to GitHub Actions and its custom domain to console.closetprayer.com. Only after GitHub has accepted that domain, add this record in Cloudflare:

SettingValue
TypeCNAME
Nameconsole
Targetqwixilver.github.io
ProxyDNS only (gray cloud) for initial setup
TTLAuto

Do not change the existing root-domain records for the prayer journal. The target has no https:// prefix or repository path. Wait for GitHub's DNS and certificate checks, enable Enforce HTTPS when available, and verify the HTTPS address before testing sign-in. GitHub recommends configuring the domain in Pages before changing DNS.

7. Test with a non-sensitive group

  1. Create a test group using the existing church-owned group guide. Use invented prayer text, not real pastoral information.
  2. Connect the owner account, choose that spreadsheet in Google Picker, and check the submissions and prayers. If consent is declined, the console should explain the problem without loading records.
  3. Share Editor access with a second test account. It should connect independently. A Viewer account must not load the administrator dashboard. No shared administrator password is needed.
  4. Confirm that group-only requests retain that label even when only one of visibility or consent permits sharing. Check that descriptions use the card width on a phone.
  5. Refresh, sign out, reconnect, revoke access in your Google account, and test loss of network. Sign-out, page reload, and session expiry should remove the console's displayed private data. Revoked file access is detected on the next API request, not instantly while a page is idle.
  6. Keep using the spreadsheet menu to approve, decline, edit, or withdraw requests. This preview has no write operation. Test those future console operations separately before enabling them for real groups.

If something does not connect

  • Origin mismatch: compare the exact website address with the authorized JavaScript origins, including the local port.
  • The API developer key is invalid: first check the API key restrictions in step 4, including the Google-hosted frame address and both allowed APIs. Account connection can succeed while the separate Picker key is rejected. If it still fails, confirm the key, OAuth client, and project number belong to the same project, and that the deployed site was rebuilt after any key-value change. Do not paste keys or access tokens into a support request.
  • Access denied: check OAuth test users, spreadsheet Editor sharing, enabled APIs, and any Google Workspace administrator restrictions. Do not make the sheet public to bypass an error.
  • Wrong template: select a configured Closet Prayer group spreadsheet with unchanged Requests and Inbox headers.
  • Session expired: connect again. The console deliberately does not store refresh tokens or automatically maintain an indefinite login.
