Closet Prayer / Administrator console

Set up the Google connection

A new-project guide for the console operator. Updated October 5, 2026.

Already connecting successfully? Keep your Google keys. Existing-group administration needs no new permissions. For the new Create a group flow, the operator completes the additional guided creation requirements once. Church administrators use the console's on-screen guide, not this Cloud-project setup.

Who does this setup?

The operator of console.closetprayer.com completes this once for the hosted console. Each church does not need its own Cloud project just to use that console. Churches keep their own spreadsheets and Apps Script deployments, and share spreadsheet Editor access with their administrators.

A self-hosted copy needs its own Google client and API key, with its own website addresses. There is no central prayer database or administrator-count restriction in this application. Google quotas and organization policies still apply.

1. Create a Cloud project

  1. Open Google Cloud's new project page with an account that will remain responsible for Closet Prayer. Give the project a recognizable name such as Closet Prayer Console.
  2. Select the new project. Record its project number from the project dashboard. This is the numeric value, not the project name or the hyphenated project ID.
  3. In APIs & Services > Library, enable Google Drive API, Google Sheets API, and Google Picker API. Keep all three in this same project.

No Firebase database, Cloud Run server, service account, or paid hosting deployment is needed by this implementation. Do not turn on unrelated services.

2. Configure Google authorization

Open Google Auth Platform > Branding inside Google Cloud Console, and confirm that your Closet Prayer project is selected at the top. Choose Get started if needed. Set the app name, a real support email, and a monitored developer contact. Use an External audience so administrators from different churches can connect. Keep the app in Testing initially and add the Google accounts you will test under Audience > Test users. Follow Google's consent-screen guide if the menu labels differ.

In Data Access, configure these scopes for ordinary administration. Guided creation has two additional scopes listed below:

openid
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/drive.file

The first three identify the connected account. drive.file gives read/write access to files selected for this app, including previously authorized files. Do not replace it with whole-Drive or all-spreadsheets access. Google supports this per-file scope for the Sheets API; it cannot be restricted to individual tabs within a selected file.

For production branding, use the console home page and https://console.closetprayer.com/privacy.html. Review that notice and your support contact before submitting them. Add closetprayer.com as an authorized domain and complete Google's ownership/branding checks as requested. Testing is not a substitute for any verification Google requires before public release.

3. Create a web OAuth client

Under Google Auth Platform > Clients, create a client of type Web application. Add these Authorized JavaScript origins:

https://console.closetprayer.com
http://localhost
http://localhost:5174
http://localhost:4175

Use only the origins you actually need. Origins have no path, trailing slash, or wildcard. Use localhost, not a Tailscale IP, for local Google sign-in testing. Mobile testing of the Google connection should use the configured HTTPS console domain.

Record the client ID, ending in .apps.googleusercontent.com. The console uses Google's browser popup flow and needs no redirect URL or client secret. Do not put a secret in source code, repository variables, or chat. See Google's client setup guidance.

4. Create and restrict the Picker API key

In the same project's APIs & Services > Credentials, create an API key and edit its restrictions immediately. If you already created the key, open that existing key rather than replacing it.

Under Application restrictions, choose Websites (HTTP referrers). Allow:

https://console.closetprayer.com/*
https://docs.google.com/*
http://localhost:5174/*
http://localhost:4175/*

The Google Docs address is required: the file picker runs inside a Google-hosted frame. Omitting it can cause The API developer key is invalid even when the key was copied correctly. These are the API key's website restrictions, not the OAuth client's Authorized JavaScript origins. See Google's explanation of Picker website restrictions.

Under API restrictions, choose Restrict key and select both Google Picker API and Google Drive API, following Google's web Picker setup example. Keep both APIs enabled in the project. The console's own Drive and Sheets reads still use OAuth; this does not broaden the requested account permissions. Keep the OAuth client, API key, and numeric project number in the same project.

Save the restrictions, allow a few minutes for the changes to take effect, then reload the console and try choosing a spreadsheet again. Changing restrictions on the existing key does not require changing the GitHub variable or rebuilding the site. If the key value itself changes, update the variable and redeploy as described below. Keep the key restricted; do not make the spreadsheet public to resolve this error.

A browser API key is visible in the published website. Restricting it is essential; hiding it in a build secret does not make it private. The key identifies the project, but does not by itself grant access to a church's spreadsheet.

5. Add the three public settings

For the hosted console, open the repository's Actions variables and add these repository variables:

NameValue
VITE_GOOGLE_CLIENT_IDThe web client ID
VITE_GOOGLE_API_KEYThe restricted browser Picker key
VITE_GOOGLE_PROJECT_NUMBERThe numeric project number

Then run Actions > Deploy console > Run workflow. These values are inserted when the site builds, so changing a variable alone does not update the live site. Missing or invalid configuration leaves Google connection disabled.

For local testing, the same three names belong in an ignored .env.local file, following .env.example. Restart the local development server after changing them. Never commit personal tokens, prayer records, a client secret, or an unrestricted key.

6. Connect the subdomain

First set the repository's Settings > Pages source to GitHub Actions and its custom domain to console.closetprayer.com. Only after GitHub has accepted that domain, add this record in Cloudflare:

SettingValue
TypeCNAME
Nameconsole
Targetqwixilver.github.io

Do not change the existing root-domain records for the prayer journal. The target has no https:// prefix or repository path. Wait for GitHub's DNS and certificate checks, enable Enforce HTTPS when available, and verify the HTTPS address before testing sign-in. GitHub recommends configuring the domain in Pages before changing DNS.

7. Test with a non-sensitive group

  1. Create a test group using the existing church-owned group guide. Use invented prayer text, not real pastoral information.
  2. Connect the owner account, choose that spreadsheet in Google Picker, and check the submissions and prayers. If consent is declined, the console should explain the problem without loading records.
  3. Share Editor access with a second test account. It should connect independently. A Viewer account must not load the administrator dashboard. No shared administrator password is needed.
  4. Confirm that group-only requests retain that label even when only one of visibility or consent permits sharing. Check that descriptions use the card width on a phone.
  5. Refresh, sign out, reconnect, revoke access in your Google account, and test loss of network. Sign-out, page reload, and session expiry should remove the console's displayed private data. Revoked file access is detected on the next API request, not instantly while a page is idle.
  6. Enable management below, then complete its write and submission checks before using real prayer data.

Guided creation: operator requirements and recovery

Pilot status: the browser flow and recovery paths have automated tests with simulated Google APIs. Before general release, verify the actual Google consent and two-stage deployment sequence with a non-sensitive church-owned test group. Keep normal existing-sheet administration available.

In the existing console Cloud project, enable Google Apps Script API. Keep Drive, Sheets, and Picker enabled and keep the same OAuth client and restricted Picker key. Add these scopes in Google Auth Platform > Data Access:

https://www.googleapis.com/auth/script.projects
https://www.googleapis.com/auth/script.deployments

The console requests these only when a person creates or resumes setup, separately from normal sign-in. Google does not restrict these scopes to one script. Update the consent description and complete any Google verification required for the expanded scopes before public rollout. Test-user access is not a substitute for verification. Do not add Drive-wide permission or loosen the Picker key.

Each church owner enables API access once in Google script settings. This is separate from enabling the API in the operator's Cloud project. See Google's API authorization explanation. Churches do not need their own Cloud project, API key, or client secret.

The wizard creates a private sheet and bound script, first deploying an owner-only approval page. The owner opens that page and approves the script's spreadsheet access. The console reads a matching receipt from the private sheet before switching that same deployment to execute as its owner, accessible to anonymous visitors. Scoped invitation keys still control the service; the sheet itself is never made public. No OAuth token is sent to the web app. The console confirms both its selected sheet and private member invitation before marking setup ready.

The generated script requests spreadsheet access and spreadsheet-menu access under its owner's account, not merely access to one selected file. The script code uses the fixed group sheet. Google may show an unverified-script warning or block deployment under Workspace policy. Do not bypass an organization's restrictions; use an approved church account/provider or ask its administrator.

Recover without creating duplicate groups

Keep the setup page open after an error. Choose Finish setup again if available. After reload/sign-in, choose the same spreadsheet to resume. A private GroupSetup tab stores the owner email, group and installation IDs, access keys, script/deployment IDs, phase, and authorization receipt. Only the original owner can finish provisioning. Other Editors can administer a completed group.

If creation stopped before returning a spreadsheet ID, check Google Drive before retrying. If the sheet exists but script creation's result is uncertain, the wizard stops rather than guessing. Open that sheet, Extensions > Apps Script, then Project Settings, and enter its Script ID in the recovery section. The console verifies its parent sheet before editing it. If no script exists, use that menu to create the bound project, then provide its ID. Never paste these setup records or credentials into a public support issue. Unneeded partial files are not automatically deleted.

Existing manual groups do not have a GroupSetup tab and are not converted by selecting them. Their member invitations remain in the church's original setup records. Guided groups show their private member invitation/QR alongside the separately labeled public form. Never put a member invitation on the public website.

Live guided-creation acceptance

  1. Sign in as a test church owner, create a fictional group, and decline the extra setup permission once. No script should be prepared without consent.
  2. Complete setup. Before Google approval, Finish setup must not activate the public service. After approval, it must identify the correct sheet and open the dashboard.
  3. Reload at the approval step and resume by selecting the same sheet. Confirm there is one script/deployment, not duplicate groups.
  4. In a signed-out browser, join through the private invitation and submit through the public iframe. Approve the request in the console and refresh in the prayer app.
  5. Repeat on an iPhone and Brave with the site-specific cookie help below. Verify real redirects, Google consent, anonymous access, and QR scanning, which mocked tests cannot prove.

Enable management for an existing group

The church spreadsheet owner completes these steps once per group. This updates the church's existing service; it does not require a new console OAuth client, a new domain, or paid hosting. First make a private copy of the spreadsheet and keep the existing script version and private setup code for recovery. Do not share those copies publicly.

  1. Open the church spreadsheet, then Extensions > Apps Script. Replace Code.gs with the updated script. Replace the manifest with the updated appsscript.json (enable showing the manifest in Project Settings if needed). Keep the existing project, spreadsheet, and CP_* script properties. Do not run Configure group with a newly generated setup code.
  2. Check that Sheets appears under Services in the script editor. The supplied manifest enables it. If missing, choose Services + > Google Sheets API > Add. For a default Apps Script Cloud project, the API is enabled automatically. If you deliberately linked a standard Cloud project, enable Google Sheets API in that script project's API Library as well. This may be a different project from the console's OAuth project. See Google's advanced service instructions.
  3. Save, then choose Deploy > Manage deployments > Edit (pencil) on the existing web app. Select New version and deploy. Keep Execute as: Me, Who has access: Anyone, and the same /exec URL. Do not create a replacement deployment address.
  4. Reload the spreadsheet. Choose Closet Prayer > Enable administrator console, review any Google authorization prompt, and paste the group's existing public submission link, not its member invitation. This creates ConsoleSettings and ConsoleCommands without clearing Requests or Inbox. Keep every tab private. If you lost the link, recover it from the church's existing form/setup records; do not create a new group as a workaround.
  5. Reload the console, connect Google, and select this sheet. You should see New prayer, Edit prayer, and review controls for pending submissions. Under Church website submissions, choose Verify service and show embed. The console checks that the service belongs to the selected sheet before showing the public link and iframe.

For a new group, complete the church-owned group setup, then run Enable administrator console with its newly generated public submission link. Re-run Enable administrator console if you rotate the public submission key. Private member invitations never belong in an iframe or a public website.

Managing requests

New prayer starts as a group-only draft. Choose Published when ready for members. Edit prayer changes wording, requested/answered status, publication, or a permitted sharing restriction. Review and approve lets you check the wording before publishing a submission; Decline leaves it privately in the Inbox. Original group-only consent cannot be widened through the console. Contact fields stay in the Inbox, so do not manually add private contact details to published wording.

Use the console or spreadsheet menu for changes. Avoid direct cell edits, row deletion, or sorting while another administrator is saving: Google Sheets does not enforce the script's lock on manual edits. A stale console edit is rejected; close its editor, refresh, and review the latest record before editing again. Members receive changes on their next successful sync, not instantly.

Interrupted saves and history

If a save loses its connection, use Check / retry this save before starting another change. After reloading, refresh the group and inspect Change history; use Check / finish pending change if needed. Signing out does not undo a change already queued in the private sheet. Pending changes expire after 24 hours. Completed changes and receipts remain in ConsoleCommands; they may include prayer wording, but not a verified author identity. This is not a tamper-proof audit log.

The pilot supports 2,000 history rows. When needed, privately archive only completed rows older than 24 hours, leaving the header intact and coordinating with other administrators. Do not remove pending rows or edit command contents. Archives also contain sensitive information.

Embed the form and test the full path

  1. Paste the console's iframe into a church test page's HTML/embed block. Its hosted form is on closetprayer.com and connects to this church's deployment. No Google administrator login or new submission subdomain is required. If your website restricts frames, allow https://closetprayer.com in its frame policy; keep a public-link alternative for visitors. Do not add a sandbox that disables scripts, forms, or origin access.
  2. Open that page in a signed-out/private browser window and on a phone. Submit invented group-only text with a test contact address. Confirm it appears only as pending in the selected sheet's Inbox, then approve it in the console.
  3. Sync a member device. Confirm the prayer appears on Daily, cannot enter Security or QR/export sharing, and does not expose the contact address. Decline another test submission and confirm it never enters the member feed.
  4. Create a draft, publish it, mark it answered, and withdraw it. Confirm each change in the spreadsheet and at the next member sync. Test allowed sharing separately using fictional data with explicit consent.
  5. Have two Editors open the same prayer. Save one edit, then the other: the older edit must report a conflict rather than overwrite the first. Submit a public request while saving another prayer; neither record should be lost.
  6. Interrupt a test save's connection, reconnect, and check/retry that same change. Verify there is only one prayer and one applied outcome. Revoke Editor access and confirm subsequent reads/writes fail. A command already submitted before revocation may still finish.

Automated tests use simulated Google responses. They cannot prove your live deployment, authorization, cross-origin redirects, or church website iframe policy. Complete these checks with non-sensitive data before using the management feature for real requests.

If something does not connect

  • Origin mismatch: compare the exact website address with the authorized JavaScript origins, including the local port.
  • The API developer key is invalid: first check the API key restrictions in step 4, including the Google-hosted frame address and both allowed APIs. Account connection can succeed while the separate Picker key is rejected. If it still fails, confirm the key, OAuth client, and project number belong to the same project, and that the deployed site was rebuilt after any key-value change. Do not paste keys or access tokens into a support request.
  • The picker stays open after confirming a spreadsheet: after 45 seconds, a Closet Prayer recovery prompt appears above Google's dialog. Choose Close picker and show diagnostics to close the picker without signing out and open the selectable report. Choose Keep choosing if you need more time; the prompt returns after another 45 seconds. Copy the report before refreshing. It contains only timestamps and fixed step names. picker-frame-message means the Google frame sent a message, not that a selection was authorized; its contents are never recorded. picker-selection-received means Google's official callback returned a selection; group-reading means the console started checking access and loading the group. Share that report, not browser network logs, which may contain access tokens.
  • No selection callback: open the console directly in a normal tab and compare the same flow in another browser, such as Edge. For Brave, see the site-only cookie workaround below. A missing callback alone does not prove cookie blocking; extensions, sessions, or other browser problems can also interfere. Do not turn off global protections, make the spreadsheet public, or remove API-key restrictions.
  • Access denied: check OAuth test users, spreadsheet Editor sharing, enabled APIs, and any Google Workspace administrator restrictions. Do not make the sheet public to bypass an error.
  • Wrong template: select a configured Closet Prayer group spreadsheet with unchanged Requests and Inbox headers.
  • Asked to connect after refreshing: this is expected. Sign-in, chosen group, and diagnostics are kept only in page memory and cleared when leaving or reloading. Connect again; spreadsheet changes and queued commands are not erased. The console deliberately does not store refresh tokens or automatically maintain an indefinite login.
  • Script upgrade required or service verification fails: follow the management upgrade above, including the manifest, Sheets advanced service, existing deployment's new version, and Enable administrator console. Confirm you used this group's public submission link. Do not loosen spreadsheet permissions or replace your working Picker key.

Brave: picker stalls with cookies blocked

Live testing confirmed a Brave configuration where the picker frame loaded but never returned a selection. Allowing cookies for the console site resolved it while Shields remained enabled. This is a confirmed workaround for that setup, not proof that every picker stall has the same cause. The console cannot detect your cookie settings.

Privacy tradeoff: Brave's Allow all cookies option permits third-party cookies for embedded content such as Google's picker on this site. It does not mean all cookies are allowed on every website. If you prefer not to make this exception, use a browser where the connection already works, such as Edge in the reported test. The console does not change browser settings for you.

  1. Open the console in Brave. If the picker is stuck, use Close picker and show diagnostics when the recovery prompt appears. Copy any report you need before reloading.
  2. Open the lion icon > Advanced controls. Keep Shields on, and change only the cookie setting to Allow all cookies for the current console site (console.closetprayer.com for the hosted version). Leave other Shields protections enabled; do not change global defaults.
  3. Reload the console, reconnect Google, and choose the spreadsheet again. Review any Google cookie or access prompt and approve it only if you agree.
  4. If the exception fixes selection, you may keep it for this site. If it does not help, restore your previous cookie setting and use the connection diagnostics to investigate further. You can remove the exception later through the same site panel.

This browser exception does not change the app's Google permission scope, spreadsheet sharing, or the personal prayer journal's database and encryption. Do not make the sheet public or loosen API-key restrictions. See Brave's cookie controls and site-specific Shields settings.
